# 107 — Stop MFA setup from silently breaking a working authenticator code

## What you asked for

The user reported being randomly locked out of a Superadmin staff account, then dug in with follow-up questions once the first (wrong) theory was ruled out:

> the auth is broken again / what is causing the 401 error? / it just randomly locks me out of superadmin account
>
> it was not an invalid code / it was the same QR scanned code, now it just keeps getting reset / is there something wrong with my env? ... since I did make a new supabase ... this started happening after I made a new supabase for dev

## What this part of the app does today

**MFA** (Multi-Factor Authentication) means logging in needs two things: your password, and a rotating 6-digit code from an authenticator app (like Google Authenticator) on your phone. This app's staff roles Admin, Supervisor, and Superadmin are *required* to have MFA turned on; the underlying mechanism used is **TOTP** (Time-based One-Time Password) — a shared secret, set up once by scanning a QR code, that both your phone and the server use to compute the same 6-digit code every 30 seconds.

Setting this up for the first time happens on the page at `/staff/mfa/enroll` (`client/src/features/auth/staff/pages/MfaEnrollPage/MfaEnrollPage.tsx`). It shows a QR code (and a manual-entry secret key) generated by a call to the server, and a box to type the 6-digit code your phone just generated to confirm the setup worked. Logging in on any later day goes through a *different* page, `/staff/mfa/verify` (`MfaChallengePage`), which just asks for that day's 6-digit code against the factor (the technical name for one enrolled authenticator entry) you already set up.

The server side of "set up MFA" lives in `enrollTotpFactor` (`server/src/shared/auth/api/supabaseAuth.api.ts`). It talks to Supabase (the database/auth service this app is built on) to create a **factor**. If Supabase says "a factor already exists" (a conflict), the code had three fallback attempts: clean up any half-finished ("unverified") factor and retry; retry once more for the same reason; and, as a last resort, delete **any** factor at all — including an already fully set-up ("verified") one — and issue a brand new secret/QR.

To stop someone from guessing codes forever, there's also a **lockout**: `mfa_lockouts` (a database table) counts wrong codes per account, and after 5 wrong codes in a row, that account can't try again for 15 minutes (`server/src/shared/services/mfaLockout/mfaLockout.service.ts`).

## What's wrong / what's missing

`/staff/mfa/enroll` has no guard stopping an *already set up* staff member from landing on it again — a bookmark, the browser's Back button, or a stale link all work, and nothing redirects them away. The enroll page calls the "set up MFA" endpoint the instant it loads, with no check for "wait, is this person already done?"

Supabase only allows removing a *verified* factor from a session that has already itself passed an MFA check (called "aal2"). That's exactly the situation of someone who's already logged in and verified today, then lands back on the enroll page by accident. So the old fallback's "last resort, delete everything" step could only ever actually succeed in exactly the one case where it must never run: an account with a real, working setup. The result: a brand new secret/QR gets silently issued, with no visible error, while the phone's authenticator app still shows the *old* entry — because nobody told it to rescan anything. Every code from that old entry is now correct for a factor that no longer exists. Five wrong-looking codes later, the account locks for 15 minutes. This can repeat indefinitely, which is exactly what the user meant by "same QR scanned code, keeps getting reset."

Investigation confirmed this had nothing to do with Supabase project switching, environment variables, or recent commits — the affected TOTP factor's own record was traced directly and had the identical, unchanged ID both before and after the fix, and no auth-related file had been touched by any other recent commit.

## What we're going to change

1. **Stop the server from ever auto-deleting a verified factor.** — _Which file:_ `server/src/shared/auth/api/supabaseAuth.api.ts`, function `enrollTotpFactor` — _Why:_ removes the one case that was silently breaking a working setup; the two earlier fallback tiers (cleaning up half-finished attempts) are untouched since they were never the problem.
2. **Make the enroll page check first before doing anything.** — _Which file:_ `client/src/features/auth/staff/pages/MfaEnrollPage/MfaEnrollPage.tsx` — _Why:_ if the status check says "already set up," redirect straight to the everyday `/staff/mfa/verify` page instead of ever calling "set up MFA" again. This closes the accidental-revisit path before it can even reach the server.

## Words you might not know

- **MFA (Multi-Factor Authentication)** — logging in needs two proofs: something you know (password) and something you have (a code from your phone).
- **TOTP (Time-based One-Time Password)** — the specific kind of MFA code used here: a 6-digit number that changes every 30 seconds, computed from a secret both your phone and the server know.
- **Factor** — the technical name, in Supabase's system, for one enrolled authenticator entry (one secret, tied to one account).
- **aal2 (Authenticator Assurance Level 2)** — a flag on your login session meaning "this session has already passed an MFA check today," as opposed to aal1 ("only a password so far").
- **Lockout** — a temporary block (here, 15 minutes) on trying more codes, after too many wrong attempts in a row, so someone can't just keep guessing.
