## Verdict: APPROVE WITH NITS

The branch replaces the `credit_expiry_enabled` boolean with a
`credit_expiry_mode` enum (`none` / `rolling` / `fixed_date`), snaps every
credit lot's `expires_at` to the end of its Asia/Manila calendar day, makes a
policy change retroactive via a new `reapply_branch_credit_expiry()`
SECURITY DEFINER RPC, enriches `GET /credits/balances` with a
FIFO-capped `next_expires_*`, and adds a customer-facing `/portal/credits`
page plus a navbar wallet pill. I checked the areas called out in the brief
(retroactive branch-set logic, FIFO agreement between the client schedule and
the server `next_expires_*`, Manila timezone maths, the validator superRefine,
RLS on the new RPC, migration ordering/backfill) and found no correctness or
security defect that blocks the PR. The findings below are robustness and
polish items.

Key checks that passed:

- **`schedule[0]` vs `next_expires_*` agree.** Server `nextExpiry`
  (`creditBalance.service.ts:73`) groups the soonest Manila day's lots,
  caps at `min(nominal, balance)`, and returns `manilaEndOfDayIso(soonestDay)`.
  Client `computeExpirySchedule` (`expiry.ts:86`) buckets ascending lots by
  Manila day and caps the first bucket at the full balance. Because
  `expires_at` is snapped to one instant per Manila day, the soonest-day lots
  are always the leading consecutive bucket, so both produce the same amount
  (`round2(min(soonest-day nominal, balance))`) and the same ISO instant
  (`YYYY-MM-DDT23:59:59.999+08:00` → `…15:59:59.999Z`). The redemption rule
  (`expire_credits()` caps oldest-first at the running balance, so spend comes
  out of the latest-expiring lot) is mirrored consistently in all three
  places.
- **Timezone maths.** Migration `20260902160`'s `(x at time zone
'Asia/Manila')::date + time '23:59:59.999') at time zone 'Asia/Manila'` and
  `creditExpiry.util.ts`'s `${key}T23:59:59.999+08:00` produce the same
  instant; Manila is a fixed +08:00 offset (no DST) so the literal-offset
  shortcut is safe. `daysUntil` compares Manila midnights, so "N days left"
  tracks the shown calendar date regardless of issuance time-of-day.
- **Retroactive branch-set.** `reapplyCreditExpiryAfterPolicyChange`
  (`staffPicker.service.ts:328`) passes `[branchId]` for an override row and,
  for the default row, every branch id minus the set that has its own
  `policy_configurations` override — which is exactly the set
  `resolveEffectivePolicy` hands the default row to. Correct.
- **RPC security.** `reapply_branch_credit_expiry` is `security definer`,
  `set search_path = public`, `revoke all … from public`, `grant execute …
to service_role` only — mirrors `issue_credit` / `redeem_credit`. Called
  through the service-role client. Fine.
- **Migration ordering / backfill.** `159`/`160` follow `…158` with no gap.
  `add column … not null default 'rolling'` backfills every row, then the
  `case when credit_expiry_enabled` UPDATE corrects the `false` rows to
  `'none'` before the column is dropped; the `fixed_date` CHECK is added after
  the UPDATE when no row is `fixed_date` yet, so it validates. No remaining
  references to `credit_expiry_enabled` outside comments.

## Non-blocking findings

### N1. Retroactive re-stamp fans out on every policy save — `server/src/features/booking/services/staffPicker.service.ts:332`

`reapplyCreditExpiryAfterPolicyChange` runs `reapply_branch_credit_expiry`
whenever any of the three `CREDIT_EXPIRY_FIELDS` is `!== undefined` in the
patch. `PolicyConfigurationPage` always sends all three fields on every save,
so changing an unrelated setting (e.g. the lunch break) re-stamps `expires_at`
on every not-yet-swept issuance lot at every override-less branch. The write
is idempotent and best-effort, so this is not a correctness bug, but it is
avoidable write amplification (and RPC surface) on an admin action that has
nothing to do with credit. Consider comparing the incoming values against the
row that was just written and skipping the RPC when they are unchanged.

### N2. Retroactive re-stamp fails silently — `server/src/features/booking/services/staffPicker.service.ts:374`

The RPC failure path is `console.error` + swallow, and the PATCH returns
`200`. The admin UI copy explicitly promises "Saving this re-applies to
credit customers already hold … not just credit issued from now on"
(`PolicyConfigurationPage.tsx:819`). If the RPC fails, that promise is
silently broken and existing lots keep their old `expires_at` with no signal
to the operator. The #117 precedent this cites is about _not losing
customer-owed credit_; here the failure mode is an invisible
policy/data mismatch. Consider returning a `reapply: 'ok' | 'failed'` flag (or
a warning banner) so the admin knows to retry.

### N3. Expiry enrichment can blank the whole balances list — `server/src/features/credits/services/creditBalance.service.ts:135`

`listCreditBalances` now `throwWithStatus(400, …)` if the added
`credit_transactions` query errors. The navbar wallet pill and
`/portal/credits` both depend on this endpoint for the raw balances; an
enrichment-query failure should degrade to `next_expires_* = null`, not fail
the balance read. Consider treating the lot query as best-effort.

### N4. `expire_credits()` cursor no longer joins `credit_balances` — `supabase/migrations/20260902159_m10_policy_credit_expiry_mode.sql:147`

The old version's inner join meant a lot with no balance row was skipped
entirely; the new version selects the balance separately and, on a NULL
result, `least(amount, greatest(NULL,0))` is NULL, so it marks `expired_at`
without writing an expiry row. This only matters in an FK-violating state that
cannot occur today — noted for completeness, not action.

### N5. `expire_credits()` / `reapply_branch_credit_expiry()` have no direct test — `supabase/migrations/20260902159…`, `…160…`

The per-iteration balance re-read (the stated reason for re-creating
`expire_credits`) and the Manila-end-of-day SQL are only exercised
indirectly through the TS services with mocked Supabase. The
multi-`fixed_date`-lot-exceeds-balance scenario the comment describes as the
bug being fixed has no regression test. A pgTAP or integration test against a
real DB would lock this behaviour in. Suites were not run here.

### N6. Client and server `next_expires_*` are unit-tested with different fixtures — `client/.../expiry.spec.ts`, `server/.../creditBalance.service.spec.ts`

Both sides are tested, but nothing asserts they return the _same_ output for
the _same_ lot set + balance. Given the brief's explicit "they must agree"
requirement, a shared-fixture parity test (even a hand-checked table) would be
worthwhile.

### N7. Past-due-but-unswept lots surface as the "next" expiry — `creditBalance.service.ts:81`, `expiry.ts`

Because neither `nextExpiry` nor `computeExpirySchedule` filters on `now`, a
lot whose `expires_at` is in the past but that the (manual/cron-gated) sweep
has not yet processed shows up as `next_expires_*` / `schedule[0]`. The
client label handles it (`describeDaysLeft` → "Expired"), but the navbar pill
can read "₱X expires <past date> · Expired" until the sweep runs. Consider
hiding or distinctly labelling already-past entries.

### N8. `credit_expiry_fixed_date` can be left stale in the DB — `booking.validator.ts:446`

The superRefine only rejects a `fixed_date` value _in the same payload_ as a
non-`fixed_date` mode. Switching mode away from `fixed_date` without
explicitly sending `credit_expiry_fixed_date: null` leaves the old date on
the row (the DB CHECK permits it). The real client always sends `null` in
that case (`PolicyConfigurationPage.tsx:267`), and nothing reads the field
unless mode is `fixed_date`, so this is cosmetic — but a direct API caller
could leave misleading data.

### N9. Stale page intro copy — `client/src/features/booking/pages/PolicyConfigurationPage/PolicyConfigurationPage.tsx:348`

The intro still says the page covers "Reschedule notice period, Staff Picker
visibility, and the fixed lunch break" — it now also has reschedule fee,
online payments, downpayment, cancellation credit, and credit expiry
sections.

### N10. `expire_credits()` remains executable by `authenticated` — `supabase/migrations/20260902159_…:181`

Pre-existing (from `20260805098`) and merely re-asserted here, but the
migration re-grants `execute … to authenticated`, so any signed-in customer
can trigger a global credit sweep directly via PostgREST RPC. Out of scope
for this branch; flagging since the grant is in the diff.
