# Code review — `perf/server-esbuild-build-dist-clean`

- **Trigger:** pre-pr
- **Base:** `dev` (merge-base `a575ec6`)
- **Reviewed:** `dev..HEAD` (1 commit, working tree clean)
- **Commits:** 1 — `ee039ca` perf(server): compile server to dist/ with esbuild instead of tsx at runtime

- **Reviewer:** code-reviewer subagent — read-only, did not author the change

## Verdict: CHANGES REQUESTED — 1 blocking, 3 nits

The change gives `server/` a real build step: `esbuild --bundle` compiles
`src/app.ts` into `dist/app.js`, `start` now runs the compiled bundle
instead of `tsx src/app.ts`, `esbuild` moved to `dependencies` (`tsx` to
`devDependencies`), a `clean` script (`rimraf dist`) was added to all three
`package.json`s, and `render.yaml`/`docs/deployment.md` were updated to
match (`npm ci && npm run build`). The core technical reasoning checks out
against the actual code (see below), and the change is otherwise sound —
but neither `.github/workflows/ci.yml` nor the local `✅ CI: Verify All`
task exercises the new `server` build at all, so a broken `npm run build`
(the exact thing this diff makes deploy-critical) would go undetected until
an actual Render deploy fails.

## Verification of the stated rationale

Checked directly rather than trusted:

- `server/tsconfig.json` has `"noEmit": true` and
  `"allowImportingTsExtensions": true` together — TypeScript refuses to
  emit JS under that combination, so a plain `tsc -b` genuinely cannot
  produce `dist/`. Confirmed.
- Every relative import in `server/src/**/*.ts` (checked with a grep for
  extensionless relative imports — none found) carries an explicit `.ts`
  extension, e.g. `server/src/app.ts:4`
  `import appRoutes from './shared/app.routes.ts'`. `tsc`'s emit (even
  without the `allowImportingTsExtensions` guard) would not rewrite these
  to `.js` in the output, so a `node`-run `tsc` build would crash on
  `ERR_MODULE_NOT_FOUND`. esbuild's `--bundle` mode sidesteps this
  correctly: bundling inlines every local `.ts` file esbuild resolves
  (it resolves the `.ts`-suffixed specifier directly and picks the right
  loader from the extension), leaving no cross-file specifier for Node to
  resolve at runtime. Confirmed.
- `--packages=external` is the right call given the dependency shape:
  `server/src` has no non-`.ts` assets read by relative path (no
  `readFileSync`/`__dirname`/`import.meta.url`/dynamic `import()` in
  `server/src`, confirmed by grep), and all of `server/package.json`'s
  runtime `dependencies` (`express`, `cors`, `dotenv`, `@supabase/supabase-js`,
  `jsonwebtoken`, `multer`, `resend`, `zod`, and the unused `golden-fur:
file:..`) are npm-resolved packages already installed via `npm ci` in
  production — externalizing them is correct and matches how `tsx` already
  ran the same imports in dev/CI today.
- Test files are correctly excluded from the bundle, but not because of
  `server/tsconfig.json`'s `exclude` (that only governs `tsc --noEmit`
  type-checking) — it's because nothing in `src/app.ts`'s import graph
  ever imports a `*.spec.ts` file. Confirmed by inspection; worth noting
  the tsconfig `exclude` is not actually doing the work the summary implies.
- Both lockfiles (`server/package-lock.json`, `client/package-lock.json`)
  are `lockfileVersion: 3` and in sync with their `package.json`
  dependency ranges (checked programmatically — no mismatches), and
  `server/package-lock.json` carries all ~78 `@esbuild/<platform>`
  optional-dependency entries needed for esbuild to install on Render's
  Linux build image. `npm ci` is safe to introduce here.
- `dist` is already covered by the root `.gitignore` (line 92), so no risk
  of an accidental `dist/` commit.

## Blocking findings

### 1. The new `server` build step has no CI/local coverage — `.github/workflows/ci.yml`, `.vscode/tasks.json`

`.github/workflows/ci.yml`'s `build-client` job runs `npm run build` for
the client, but there is no equivalent `build-server` job — the workflow
never runs `npm run build` (i.e. the `esbuild` command) for `server/` at
all. The local `✅ CI: Verify All` composite task
(`.vscode/tasks.json:160-166`) has the same gap: its `dependsOn` list
includes `🏗️ Client: Build` but no server build task, and no such task is
even defined in the file.

This matters specifically because of what this diff changes: before this
branch, `server`'s "build" was just running `tsx`, which vitest already
exercises indirectly every time tests run (same TS-to-JS path). After this
branch, production boot depends on a distinct code path — `esbuild
--bundle` resolving and inlining the entire `server/src` import graph —
that is exercised by _nothing_ in CI or in the documented local
verification flow. A bad relative import path, a case-sensitivity mismatch
between an import specifier and the actual filename (Windows dev is
case-insensitive; Render's Linux build image is not — this class of bug
specifically would pass `tsc --noEmit` and `vitest` on a contributor's
Windows machine and only surface at deploy time), or any future non-`.ts`
asset added under `server/src` that needs copying rather than bundling,
would all pass every existing check and only be caught by a live Render
deploy failing its health check — precisely the failure mode this PR is
otherwise trying to make the deploy pipeline more robust against.

Fix direction: add a `build-server` job to `ci.yml` (`npm ci && npm run
build` in `server/`, mirroring `build-client`) and a matching `🏗️ Server:
Build` task wired into `✅ CI: Verify All` in `.vscode/tasks.json`.

## Non-blocking findings

### N1. `esbuild`'s in-production-dependencies placement isn't self-documenting — `server/package.json:29`

The reason `esbuild` sits in `dependencies` rather than `devDependencies`
(Render's build environment sets `NODE_ENV=production`, and npm's
documented `omit` default becomes `dev` whenever `NODE_ENV=production` is
set and no explicit `--include=dev`/`--omit` override is passed, so a
plain `npm ci` there would otherwise skip it) is non-obvious to a future
reader and easy to "fix" backwards by moving it back to devDependencies.
Worth a one-line comment or a note in `docs/deployment.md` next to the
build command, since `package.json` has no comment syntax.

### N2. `golden-fur: file:..` sits in `dependencies` unused — `server/package.json:31`

Pre-existing (not introduced by this diff) and not part of this review's
scope, but grep found no import of it anywhere in `server/src`. Since this
diff is specifically auditing what's true "production dependency" for the
new build/deploy path, flagging it here: it's dead weight in the
externalized-package set esbuild has to resolve, and one more thing
`npm ci`'s production install has to materialize on every Render build for
no runtime benefit.

### N3. `clean` isn't part of the Render build command — `render.yaml:19`

The new `clean` (`rimraf dist`) scripts are never invoked by
`buildCommand: npm ci && npm run build`. This is very likely fine in
practice (Render's free-plan builds run in a fresh environment each
deploy, and `esbuild`'s single `--outfile` overwrites cleanly even if a
stale `dist/app.js` were present), but since the commit message frames
`clean` as part of this change's purpose, it's worth confirming that
assumption holds rather than leaving `clean` as a local-only convenience
that the deploy path silently doesn't use.
