## Verdict: APPROVE (findings addressed)

The change adds a hydrated `GET /bookings/:id/details` endpoint feeding a
shared `BookingDetailsView` used by a new customer `BookingDetailsModal`
(opened from the My Bookings `…` menu) and the refactored staff
`BookingDetailsPage`; plus adds `Cashier` to `PET_LOOKUP_ROLES` /
`PROFILE_LOOKUP_ROLES`. No correctness/security defect in the auth model —
`getBookingById` remains the single gate (owner-or-staff). The review
surfaced five findings; the four with user-facing impact were fixed before
this report, the fifth is accepted as-is.

## Findings

### F1 — payment data widened to non-billing staff roles — FIXED

The new endpoint's `getBookingById` admits any staff role, so a
Groomer/Veterinarian/Pet Assistant opening `/staff/bookings/:id` would have
seen `payment_reference` / `bank_name` / `payment_method` / amounts that
`GET /billing/booking/:id/transactions` (`BILLING_STAFF_ROLES`) previously
withheld from them.
**Fix:** `bookingDetails.service.ts` now resolves the caller's staff role
and passes `includePayments` to `resolveTransactions` — `false` for a staff
caller outside `BILLING_STAFF_ROLES`, which returns `[]`. New
`payments_visible: boolean` on `BookingDetails`; `BookingDetailsView` hides
the entire Payments section (list + paid/balance rollup) when it's false.
The owning customer always sees their own payments (already exposed via
`GET /reports/my-transaction-history`). Covered by a new
"withholds the payment list from a non-billing staff role (Groomer)"
integration test.

### F2 — grouped-booking Pricing section never reconciled — FIXED

For a multi-booking-checkout member, `items_subtotal` was this booking's
items (e.g. ₱630) while `total` was `group.net_total` (e.g. ₱1417.50), so
"Subtotal ₱630 … Total ₱1417.50" read as broken.
**Fix:** `BookingDetailsView` relabels the section for a grouped booking —
"This booking's services" / "Bundle discount" / "Bundle promo" / "Bundle
total" / "Bundle down payment" — with a leading explanatory line, so the
numbers are self-consistent as labelled (this booking is one share of a
larger bundle). No server change; `items_subtotal` stays this booking's.

### F3 — swallowed transactions-query error → wrong balance — FIXED

`resolveTransactions` ignored the query `error`; on any read failure
`amount_paid` became 0 and `balance_due` became the full total, telling a
paid customer they still owe money.
**Fix:** `resolveTransactions` and `resolveGroup` now
`throwWithStatus(400, …)` on error (both feed the pricing rollup — a
grouped booking's basis lives entirely on the group row).

### F4 — `downpayment_amount` not coerced — FIXED

Every other numeric field runs through `num()`; `downpayment_amount` was
passed raw, so its runtime type was a PostgREST `numeric` string despite
the declared `number | null`.
**Fix:** new `numOrNull()` helper (coerces, preserves `null`); applied to
`pricing.downpayment_amount`.

### F5 — extra serial round-trip for discount/promo names — ACCEPTED

For a non-grouped booking with a `selected_discount_id`/`selected_promo_id`,
the name lookups run in a second `await` after the main `Promise.all`
rather than inside it. Only the grouped case genuinely needs `group`
resolved first. Impact is one extra indexed round-trip on a
rarely-hit read path (customer/staff opening one booking's detail view);
folding it in would mean branching the query plan on `booking_group_id`.
Left as-is — not worth the added complexity for a single-request read.
