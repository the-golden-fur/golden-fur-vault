`true` at 50% Percentage; (2) replaces the app-side `createInitialBookingCharge`
with a `create_initial_booking_charge` SECURITY DEFINER RPC that emits **two**

One real issue was found and fixed during review (F1). The rest are nits.

### Fixed during review

**F1. `payForBooking` could insert a charge beside a still-Pending one** —
`customerBookingPayment.service.ts`. The rewrite picked at most one Pending row
and, finding none, inserted a fresh row. With the two-transaction downpayment
model a booking can already carry a Pending row from creation, so a direct API
call (`pay_in_full` mismatch) could stack a second charge and over-collect.
Fixed in `34f1a08`: it now falls back to any existing Pending row before
inserting, and the "pay just the down payment" path bills the down-payment
portion regardless of which row it lands on. Not reachable from the portal UI
(the client derives `pay_in_full` from the clicked row's `payment_choice`).

Key checks that passed:

- **Migration ordering.** `20260902161`–`165` follow `…160` with no gap.
  `settle_transaction` is `drop`-then-`create` (a new trailing
  `p_amount_applied` arg changes the signature) based on the current
  `20260901153` body; `pay_transaction_with_credit` and `add_booking_payment`
  are `create or replace` (signatures unchanged) based on `20260901158` /
  `20260901154`. Nothing between those and HEAD redefines them.
  `get_staff_availability()` is untouched.
- **No stale 6-arg `settle_transaction` caller.** Grep of `server/src` +
  `supabase/migrations` for `settle_transaction`: the only invocation is
  `transactionPayment.service.ts`, which now always passes `p_amount_applied`.
  The other references are prose in migration comments.
- **Both spawn rows are `Pending`, so every rollup still reads them as
  unsettled.** `SLOT_HOLD_PAID_OR_FILTER` (`payment_status != 'Pending'`),
  `settle_transaction` / `add_booking_payment` / `recomputeBookingPaymentStatus`
  rollups (`payment_status <> 'Pending'`), and `payableBalances` all exclude
  the new balance row until it settles. A downpayment booking still lands
  `payment_status = 'Pending'`, still a pencil booking, until the first row is
  actually paid.
- **Rounding.** `create_initial_booking_charge` takes the already-`round2`'d
  `netTotal` and `downpaymentAmount` from `createBooking`; `v_balance = net −
v_dp` is exact. `settle_transaction`'s `v_leftover = round(v_full − v_applied,
2)` with a `> v_full + 0.001` guard on the applied amount. `numeric(10,2)`
  columns.
- **`applyFirstBookingPaymentSideEffects` fires once.** With two upfront rows,
  the first settlement moves `bookings.payment_status` off `Pending` and fires
  the held-back `booking_confirmed` / `staff_assigned`; the second settlement's
  `paymentStatusBefore` is `Partially Paid`, so the `:1711` guard makes it a
  no-op. (No dedicated test — see G2.)
- **Cash tender vs amount applied.** `recordTransactionPayment` passes
  `applied` (not the full transaction total) as `amountDue` into
  `resolvePaymentConfirmation`, so the Cash tender floor and the change
  calculation are against what the cashier is actually collecting.

## Non-blocking findings

### N1. `settle_transaction` line-item shrink assumes exactly one line item — `supabase/migrations/20260902163_…:101`

`update transaction_line_items set unit_price = v_applied, line_total =
v_applied where transaction_id = p_transaction_id` sets every line item on the
transaction to the applied amount. This is correct only because every
`booking_payment` transaction is created with exactly one line item
(`create_initial_booking_charge`, `add_booking_payment`, `payForBooking`, and
the spawn itself). A future multi-line `booking_payment` row would break the
`SUM(line_total) = total_amount` invariant here. Documented in the migration
comment; worth a `raise exception` guard on `count(*) <> 1` if that ever
becomes possible.

### N2. `loadSpawnedLeftover` id-set diff is racy under concurrent settles — `server/src/features/billing/services/transactionPayment.service.ts:45`

`pendingBalanceTxnIds` (before) vs a re-query (after), returning the first
Pending `balance` id not in the "before" set. If two partial settlements on the
same booking interleave, each could report the other's spawn. Impact is
cosmetic only — the value is surfaced to the cashier as "a balance charge was
created", never used for a write. A cleaner fix would be for the RPC to
`RETURNS` the spawned row id, but that changes the return type across three
call sites.

### N3. Credit path ignores the modal's "amount to collect" — `client/src/features/reports/components/TransactionHistoryTable/TransactionHistoryTable.tsx:188`

When the method is `Credit`, `confirmPay` calls `payTransactionWithCredit(id)`
with no amount; the RPC applies `min(available, charge)`. The amount field is
hidden for `Credit` (`payIsCredit ? null : <field>`), so the UI isn't
misleading, but a cashier who wants to apply only part of a customer's credit
to a charge can't — they'd have to split first. Deliberate for this pass;
`payTransactionWithCredit` could take an optional `amountApplied` later.

### N4. `'Credit'` widens `PaymentFields.payment_method` only by cast — `client/.../PaymentMethodForm.tsx:40`, `TransactionHistoryTable.tsx:170`

`PaymentFields.payment_method` stays `PaymentMethod` (no `'Credit'`); the two
call sites compare with `(x as string) === 'Credit'` and the form's `<select>`
onChange stores `'Credit'` via `as PaymentFields['payment_method']`. Works at
runtime, `'Credit'` never reaches the `/pay` endpoint (routed to
pay-with-credit). Slightly unsound; a `PaymentMethod | 'Credit'` alias local to
this modal would be cleaner, but widening `PaymentFields` itself rippled into
`CashierCheckoutPage` / `MiscellaneousSaleForm` (tried, reverted).

### N5. Policy default flip is guarded against admin-set values — `supabase/migrations/20260902161_…:31`

The `update … where branch_id is null and downpayment_type is null and
downpayment_amount is null` only flips the seeded default row when its
type/amount were never set. On a shared DB where an admin previously set
type/amount but left `downpayment_enabled = false`, downpayment stays off —
arguably respecting their choice, but the migration's intent ("on by default")
isn't universal. Fresh installs (migration-seeded row has null type/amount) get
the flip. Intentional; noted so the deploy isn't a surprise.

### N6. Redundant condition in the charge guard — `server/src/features/booking/services/booking.service.ts:1064`

`if (requiresUpfrontCharge && !nothingOwed && netTotal > 0)` — since
`nothingOwed = requiresUpfrontCharge && netTotal <= 0`, the `!nothingOwed`
term is implied by `netTotal > 0` when `requiresUpfrontCharge` is true. Reads
clearly enough; no change needed.
