## Verdict: CHANGES REQUESTED

The change replaces two hardcoded Grooming→Groomer/Veterinary→Veterinarian
maps with an admin-configurable `service_types.eligible_staff_roles` array,
drops the redundant `policy_configurations` Staff Picker toggle, removes the
client-supplied `key` field on Service Types, seeds a missing Assessment
`service_types` row, and fixes a `resolveStaffAssignment` bug that silently
dropped staff preference for any category outside Grooming/Veterinary. The
application-layer work (client, server services, validators, tests) is
solid and well covered by updated specs. One migration, however, drops and
recreates `get_staff_availability()` under a new signature without
re-applying the `revoke ... from public` / `grant ... to authenticated,
service_role` pair the function has carried since it was first locked down
— an access-control regression that must be fixed before this ships.

## Blocking findings

### 1. `get_staff_availability()` loses its access-control grants on redefinition — `supabase/migrations/20260904169_m03_get_staff_availability_multi_roles.sql:21-23`

This migration does `drop function public.get_staff_availability(public.staff_role, uuid, timestamptz, timestamptz, uuid, uuid);` followed by `create function public.get_staff_availability(p_roles public.staff_role[], ...)`. Every prior redefinition of this RPC (`20260701014`, `20260714031`, `20260728062`, `20260804092`, `20260808109`, `20260829148`, `20260901156`) used `create or replace function`, which preserves existing grants. This one changes the parameter list, so it can't use `create or replace` and has to drop first — but `DROP FUNCTION` discards the function object entirely, including any grants against it, and PostgreSQL grants `EXECUTE` to `PUBLIC` by default on a freshly created function.

The function was deliberately locked down when it first went production-facing (`supabase/migrations/20260718036_m03_get_staff_availability_rpc.sql:157-165`):

```sql
revoke all on function public.get_staff_availability(...) from public;
grant execute on function public.get_staff_availability(...) to authenticated;
grant execute on function public.get_staff_availability(...) to service_role;
```

20260904169 has no equivalent `revoke`/`grant` block. After this migration runs, `get_staff_availability` reverts to the Postgres default — executable by `PUBLIC`, which includes `anon`. Concretely: an unauthenticated caller can now hit the Supabase REST RPC endpoint directly (`POST /rest/v1/rpc/get_staff_availability`, no Authorization/anon-only) and enumerate a branch's staff roster (`staff_id`, `display_name`, `profile_photo_url`) and their live availability windows, bypassing the Express API entirely. This is exactly the exposure the original `revoke ... from public` was written to prevent, and it's silently undone by this migration. (The Express server itself calls this RPC with the service-role key, so the app's own booking flow won't visibly break — which makes this easy to miss in manual testing — but the direct-`anon`-access hole is real.)

Fix: append the same `revoke all ... from public; grant execute ... to authenticated; grant execute ... to service_role;` block (against the new `staff_role[]` signature) to this migration, immediately after the `create function` statement.

## Non-blocking findings

### N1. `eligible_staff_roles` isn't validated against the staff-role enum — `server/src/features/maintenance/modules/validators/maintenance.validator.ts:435,451`

Both `createServiceTypeValidator` and `updateServiceTypeValidator` accept `eligible_staff_roles: z.array(z.string()).optional()` — any string passes Zod, not just the eight real `StaffRole` values. Postgres will reject an invalid value at insert/update time (the column is `staff_role[]`), so this degrades to a raw Postgres error surfaced as a generic 400 rather than a clean Zod validation message, and the client only prevents bad values because `StaffRoleMultiSelect` happens to enumerate `ALL_STAFF_ROLES` itself. Tightening to `z.array(z.enum(ALL_STAFF_ROLES_AS_CONST))` (there's already a server-side `ALL_STAFF_ROLES` in `server/src/features/staff/staff.types.ts`) would give a proper validation error and match the "Zod validation on both client and server for new request/response shapes" convention the rest of the codebase follows.

### N2. All 8 roles (including non-operational ones) are selectable in the Staff Picker multi-select — `client/src/features/maintenance/components/StaffRoleMultiSelect/StaffRoleMultiSelect.tsx:46`

`StaffRoleMultiSelect` iterates the full `ALL_STAFF_ROLES` list, so an admin can mark `Superadmin`, `Admin`, `Cashier`, etc. as eligible for a category's Staff Picker, not just the operational roles (`Groomer`, `Veterinarian`, `Pet Assistant`, `Receptionist`) that would ever plausibly staff a booking. Nothing downstream stops this — `get_staff_availability` will happily match against `staff_profiles.role = any(p_roles)` for any role. Likely harmless in practice (there won't be many active `staff_profiles` rows with those roles at a branch), but worth a second look on whether the picker should exclude the four admin/back-office roles.

## Test coverage

Test coverage for the application-layer change is thorough: `staffPicker.service.spec.ts`, `booking.service.spec.ts`, `availability.service.spec.ts`, `capacity.service.spec.ts`, `reschedule.service.spec.ts`, and `booking.integration.spec.ts` were all updated to route through the new `resolveServiceTypeStaffConfig` lookup instead of the old hardcoded map, and `CustomerBookingFlowPage.spec.ts` / `AdminServiceTypesPage.spec.ts` / the new `StaffRoleMultiSelect.spec.ts` cover the client side (including the "mock leaks across tests" trap the flow-page spec's comment calls out). No test exercises the migration's Postgres-level grants (out of scope for a Vitest suite; the Blocking finding above is a SQL-migration issue, not something the app-level test suites would ever catch — a `psql`-level check, e.g. `has_function_privilege('anon', 'get_staff_availability(...)', 'EXECUTE')`, would be the only way to catch this class of regression). Suites were not run here per this agent's read-only scope.
