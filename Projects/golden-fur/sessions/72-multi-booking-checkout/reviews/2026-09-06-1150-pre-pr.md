## What was checked

- **Money math**: combined discount/promo/downpayment computation against
  the group's total is exercised by `bookingGroup.service.spec.ts` test (a)
  with exact expected numbers (450 combined − 50 flat discount − 45 (10%)
  promo = 355 net, downpayment 100 flat) — matches `createBooking`'s own
  discount-before-downpayment ordering.
- **Rollback completeness**: test (c) confirms a post-insert capacity loss
  on one sub-booking deletes every row inserted for the whole request (not
  just the loser), matching the "all-or-nothing" design intent.
- **In-request capacity guards**: tests (b)/(b2)/(b3) confirm two
  sub-bookings in the same request can't claim the same staff slot, the
  same pet can't end up double-booked at an overlapping time (Online), and
  that guard is correctly skipped for Walk-in.
- **Non-regression**: `booking.service.spec.ts` (the pre-existing
  single-booking suite, 70+ tests) passes unchanged — `createBooking()`
  itself was not modified, only additive exports.
- **Schema constraint**: the widened `transactions_booking_id_matches_type`
  CHECK is a strict superset of the prior constraint (verified by reading
  the live constraint text before writing the migration) — no backfill
  needed, no existing row can violate it.
- **Group-of-1 bypass**: `handleSubmit` branches on `bookingsList.length`
  client-side; a single booking still calls the untouched `createBooking`/
  `POST /bookings`, so the common case has zero behavioral change.
