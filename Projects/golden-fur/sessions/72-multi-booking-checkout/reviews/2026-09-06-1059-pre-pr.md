## Verdict: CHANGES REQUESTED

The change adds `booking_groups` (several independent bookings sharing one
discount/promo/downpayment/payment-scheme and one shared transaction or
downpayment+balance pair), a same-checkout same-pet time-conflict guard
(client `SlotPicker` exclusion + server in-request capacity guard), and
group-aware variants of `settle_transaction`/`pay_transaction_with_credit`/
the webhook confirmation path. The new-money-path plumbing (webhook,
counter-payment, credit-payment, initial-charge RPCs) is careful and
well-mirrored off the existing single-booking equivalents. However, several
places that already exist elsewhere in the codebase were **not** made
group-aware, and two of those are money/booking-status correctness bugs; one
client-side computation doesn't match its own server-side counterpart. None
of these is a security hole or literal data-loss risk, so this stops short
of BLOCK, but each below must be fixed before merge.

## Blocking findings

### 1. Cancelling one booking inside a group forfeits the credit it's owed — `server/src/features/booking/services/cancellation.service.ts:35-48`

`cancelBooking` (unchanged by this diff) computes the cancellation-credit
amount via `confirmedAmountPaid(bookingId)`, which sums `transactions` rows
filtered by `.eq('booking_id', bookingId)`. For a grouped booking, every
payment transaction has `booking_id = null` and `booking_group_id` set
instead (per the new, deliberately mutually-exclusive
`transactions_booking_id_matches_type` CHECK,
`supabase/migrations/20260906174_...sql`). So `confirmedAmountPaid()` always
returns `0` for a booking created via `createBookingGroup`, even when the
group's shared transaction was fully settled — `cancelBooking` silently
issues **zero credit** for a customer who met the notice period and did pay.
Per `.agent/skills/credit-balance-ledger.md`, "amount paid" must be summed
from the booking's settled `booking_payment` transactions; that invariant is
broken for every grouped booking. `cancelBooking` itself is still fully
reachable for one booking inside a group — nothing gates it off — so this
isn't a hypothetical path.

Fix direction: `confirmedAmountPaid` (or a caller) needs a group-aware
variant that, for a grouped booking, attributes a fair share of the group's
settled transactions to this one booking (e.g. pro-rated by
`total_price`/`net_total`), or the whole cancellation flow needs its own
group-counterpart the way `recomputeBookingPaymentStatus` got
`recomputeBookingGroupPaymentStatus`.

### 2. A single cancelled sibling permanently blocks the whole group's cashier checkout — `server/src/features/billing/services/lineItemSources.service.ts:69-75`, `checkoutAggregation.service.ts:446-456`

`getBookingForBilling` throws 409 unless `status === 'Completed'`.
`buildGroupCheckoutPreview` (and therefore `checkoutBookingGroup`) loops
`getBookingForBilling` over **every** booking under `booking_group_id`
sequentially and lets the first throw propagate. This group-checkout path
exists specifically for a Veterinary-inclusive/-only group, whose upfront
charge is never created (`requiresUpfrontCharge` false or the group is a mix
that still needs a real post-visit charge). If any one sibling in that group
is cancelled — via the ordinary, unmodified `/bookings/:id/cancel` route,
which has no group awareness (see #1) — `buildGroupCheckoutPreview` throws
on that sibling every single time, and the cashier can never bill the group
for the OTHER, completed bookings. There's no test exercising a
partially-cancelled group through this path (`bookingGroup.service.spec.ts`
only exercises pure-Veterinary and all-discounted groups).

Fix direction: exclude Cancelled/No-show siblings from the group checkout
loop (and from the group's own subtotal), rather than letting one non-
Completed sibling anywhere in the group hard-fail the whole preview.

### 3. `recomputeBookingGroupPaymentStatus`'s bulk update overwrites every sibling's `payment_status`, including ones that are Cancelled/No-show/Completed — `server/src/features/booking/services/booking.service.ts:1908-1917`

```ts
const { error: bulkUpdateError } = await supabase
  .from('bookings')
  .update({ payment_status: nextStatus, ... })
  .eq('booking_group_id', bookingGroupId);
```

This has no `status` filter, unlike the single-booking path (which only
ever touches the one booking it's rolling up). If one sibling in a group was
individually Cancelled (see #2) or reached Completed, and a _later_ payment
against the group's shared transaction pushes the group to
`Fully Paid`/`Partially Paid`, that Cancelled/Completed sibling's own
`payment_status` gets silently rewritten too — e.g. a Cancelled booking can
end up reporting `payment_status: 'Fully Paid'`, which is read directly by
DSR/queue/report code elsewhere in the app as "this booking is settled".
`previouslyPending` (used just below for the side-effects loop) already
demonstrates the pattern needed — filter the bulk update the same way, or at
minimum exclude terminal statuses (Cancelled/No-show) from it.

### 4. Mixing Veterinary into a group forces its price to be charged upfront, unlike a standalone Veterinary booking — `server/src/features/booking/services/bookingGroup.service.ts:292-295`

```ts
const requiresUpfrontCharge = resolvedSubBookings.some(
  (sub) => sub.serviceCategory !== "Veterinary",
);
```

For a single booking, `createBooking` skips the upfront charge entirely
whenever the category is Veterinary — full stop, no upfront collection,
"priced during the visit" (see the comment at `booking.service.ts:902`,
`requiresUpfrontCharge = input.service_category !== 'Veterinary'`). Here,
`requiresUpfrontCharge` is `true` the moment **any** sub-booking is
non-Veterinary, and `combinedNetTotal` (which includes the Veterinary
sub-booking's own `totalPrice`, computed the same way as any other category
via `resolveBookingItems`) is charged upfront via
`create_initial_booking_group_charge` for the **whole cart**, Vet share
included. A customer who bundles a Grooming appointment with a Vet visit
therefore pays for the Vet visit upfront — a real behavior change from the
established "Vet is priced during the visit, never charged upfront" rule,
introduced silently and with no test covering a mixed
Veterinary/non-Veterinary group (`bookingGroup.service.spec.ts` test (d)
only covers an all-Veterinary group).

Fix direction: either exclude each Veterinary sub-booking's own price from
`combinedNetTotal`/the upfront charge (charging only the non-Vet share
upfront, same as today's per-category split), or explicitly document this as
an intentional scope decision for mixed carts and add a test for it — as
written it reads as an oversight, not a decision.

### 5. Client discount filtering doesn't match the server's "exactly one category" rule for a multi-category cart — `client/src/features/booking/pages/CustomerBookingFlowPage/CustomerBookingFlowPage.tsx:1371-1376` vs. `server/src/features/booking/services/bookingGroup.service.ts:247-251`

Server-side, a category-scoped discount only ever matches when the whole
group is a single category:

```ts
const uniformCategory =
  subBookingCategories.size === 1 ? [...subBookingCategories][0] : undefined;
```

Client-side, the equivalent filter is:

```ts
return groupCategories.has(discount.scope_category as ServiceCategory);
```

`groupCategories` is the **set** of every category across the whole cart —
`.has()` is true as soon as _any_ booking in the cart matches, regardless of
how many other categories are also present. So for a two-category cart
(e.g. Grooming + Hotel) with an active Grooming-scoped discount, the client
still lists that discount as applicable and lets the customer select it
(and, if it's Senior/PWD, walks them through the ID-verification
attestation) — but `resolveDiscountAndPromo` server-side will always reject
it (`uniformCategory` is `undefined` for a 2-category cart, so the
`scope_type === 'category'` branch never matches), throwing 400 at final
submit. This is a real, reachable dead end at the very last step of a
otherwise-complete checkout, not a hypothetical edge case — mixing
categories in one cart is the entire point of this feature, and there's no
test for a mixed-category cart with a category-scoped discount selected.

Fix direction: `applicableDiscounts`'s category-scope check needs to mirror
the server exactly — `groupCategories.size === 1 && groupCategories.has(...)`.

### 6. A Walk-in sub-booking bundled with an Online one is silently pulled into the group's downpayment/slot-hold gate and skips its own post-insert capacity re-check — `server/src/features/booking/services/bookingGroup.service.ts:276-297`, `:434-446`

`downpaymentRequired`/`holdsSlot` are computed **once, for the whole
group**, off `hasOnlineSubBooking` and the branch policy — not per
sub-booking. `booking_source` is genuinely independent per sub-booking
(`bookingGroupItemValidator` allows it per entry, and client-side each
"Add another booking" pass re-visits the `bookingType` step and stores its
own `bookingSource` on that entry's `SubBookingDraft`), so a receptionist
mixing a Walk-in pet with an Online one in the same checkout is a reachable
combination. When that happens and the branch has downpayment enabled:

- `holdsSlot` is `false` for the **whole group**, so step 10's post-insert
  race re-verification (`confirmCapacityAfterInsert`, the AC-5 backstop
  documented in `capacity-based-scheduling.md`) is skipped for **every**
  sub-booking in the group — including the Walk-in one, which is inserted
  directly as `status: 'In Progress'` (physically happening right now,
  per `booking.service.ts`'s own single-booking rule: "a walk-in never
  touches the down payment policy... no slot-holding risk"). That
  contradicts the single-booking behavior, where a Walk-in booking's
  `holdsSlot` is always `true` (its `downpaymentRequired` is never set,
  since the whole downpayment block is gated on `bookingSource === 'Online'`
  there) and always gets the post-insert race check.
- The Walk-in sub-booking's own share of the group charge is bundled into
  the downpayment/balance split, meaning a physically-present, already-
  in-progress walk-in service can end up gated behind an unpaid "pencil
  booking" downpayment mechanic that exists specifically to manage the risk
  of an _unconfirmed, not-yet-present_ Online customer.

Fix direction: gate `holdsSlot`/the per-booking capacity re-check on each
sub-booking's own `bookingSource`, the same way the single-booking flow
does, rather than on a single group-wide flag — a Walk-in sub-booking should
always hold its slot and always get its own AC-5 re-check, group or not.

## Non-blocking findings

### N1. Three `as unknown as X` casts bypass type-checking in `resolveSubBooking` — `server/src/features/booking/services/bookingGroup.service.ts:253-264, 587-594, 637-643`

`resolveDiscountAndPromo`, `resolveFreePackageAward`, and
`resolveStaffAssignment` are all typed to take a full `CreateBookingInput`;
`bookingGroup.service.ts` passes a partial object shape and casts it via
`as unknown as Parameters<typeof fn>[0]` in three places. Verified each
function only reads the fields actually supplied, so this is functionally
correct today, but it's a maintenance trap: if any of those three functions
is later changed to read one more field off `CreateBookingInput`, the
group-checkout call site will silently pass `undefined` with no compiler
error. Consider narrowing each function's parameter type to only what it
actually uses (a `Pick<...>` or a dedicated interface) so both call sites
stay honest without the cast.

### N2. `create_initial_booking_group_charge` trusts `p_net_total` as a bare parameter rather than the row it just locked — `supabase/migrations/20260906175_m08_create_initial_booking_group_charge_rpc.sql:35-67`

The RPC `select ... for update`s the `booking_groups` row (which already has
`net_total` computed and stored server-side) but then uses the caller-
supplied `p_net_total` parameter for all the math instead of `v_group.
net_total`. This exactly mirrors the pre-existing single-booking
`create_initial_booking_charge` (20260902162), so it isn't a new pattern
introduced by this diff — flagging only because the new file had the chance
to read `v_group.net_total` directly (it already selects the full row) and
didn't, keeping two sources of truth for the same value in sync by
convention rather than by construction.

### N3. `bookingGroup.service.spec.ts` — good coverage of the capacity/rollback paths, but no mixed-category or mixed-Veterinary case

Tests (a)-(e) cover combined discount/promo math, the in-request staff/cage/
same-pet conflict guard, post-insert rollback, all-Veterinary (no upfront
charge), and full-discount. There's no test for: a group spanning >1
category with a category-scoped discount selected (would have caught #5 on
the client, and made the server's `uniformCategory` "fail safe" behavior
explicit at the group layer), a mixed Veterinary + non-Veterinary group's
charge amount (would have caught #4), or a group with mixed `booking_source`
(would have caught #6).
