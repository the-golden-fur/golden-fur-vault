## Verdict: CHANGES REQUESTED

The change splits the overloaded `policy_configurations.notice_period_days` into
a new `booking_notice_period_days` column (default 0) for the new-online-booking
lead-time floor, leaving `notice_period_days` as the reschedule/cancellation
notice. It threads a `intent: 'new_booking' | 'reschedule'` parameter through the
availability endpoint, `getDaySlots`, the client `SlotPicker` and the two
reschedule pickers, adds `bookingLeadDays` / `resolveBookingLeadDays` /
`assertMeetsBookingLeadTime` in `staffPicker.service.ts`, and makes
`getDaySlots`'s "start already past" filter run only when the requested date is
today in branch tz (the reported future-date slot-shift bug). The migration,
type wiring, validators and effective-policy merge are all handled cleanly and
the timezone/calendar-date math in both `assertMeetsBookingLeadTime` and
`getDaySlots` is correct. The blocking issue is a side effect: at the new default
config nothing rejects an Online booking whose `scheduled_start` is in the past.

## Blocking findings

### 1. Past-dated Online bookings are no longer rejected at the default config — `server/src/features/booking/services/booking.service.ts:841`, `server/src/features/booking/services/staffPicker.service.ts:223`

Before this change, `createBooking` called
`assertMeetsNoticeLeadTime(policy, input.scheduled_start)` for every Online
booking. The seeded default policy row (`20260718037_..._stub.sql:21-29`) has
`notice_enforcement_enabled = true` and `notice_period_days = 3`, so that gate
rejected any Online `scheduled_start` less than 3 days out — which incidentally
also rejected slots in the past or earlier today.

After this change `createBooking` calls `assertMeetsBookingLeadTime`, which reads
the new `booking_notice_period_days` column. Its default is `0`, and the function
short-circuits on `if (!leadDays || leadDays <= 0) return;`
(`staffPicker.service.ts:228-229`). No other check in `createBooking` or in
`createBookingValidator` (`booking.validator.ts:203-270`, whose only temporal
refine is `scheduled_end > scheduled_start`) constrains `scheduled_start` to the
future. So on a stock deployment a direct `POST /bookings` with
`scheduled_start` set to yesterday — or to 08:00 today at 15:00 — now succeeds:
it resolves staff / capacity against a past window, can attach a downpayment
transaction and can consume a free-package award, then gets flipped to No-show by
`markPastPendingAsNoShow`. The Slot Picker hides these client-side (past dates
return `[]`, today filters past starts) but the server no longer enforces it.

This also makes the code comments inaccurate: `booking.service.ts:835-837` and
`staffPicker.service.ts:220-221` both describe `assertMeetsBookingLeadTime` as
"the authoritative gate … a direct API call can't book inside the window", which
is false whenever `booking_notice_period_days` is 0 (the default).

Direction of a fix: add an explicit "`scheduled_start` must not be in the past"
check that is independent of the notice knob — either a refine in
`createBookingValidator` or an unconditional guard in `createBooking` before the
`bookingSource === 'Online'` block (walk-ins legitimately book "now", so allow a
small tolerance or scope the check to Online). Add a test that a past-dated
Online booking is rejected.

## Non-blocking findings

### N1. `nextAvailableSlotQueryValidator` accepts `intent` but nothing consumes it — `server/src/features/booking/modules/validators/booking.validator.ts:537`

The validator gained `intent: z.enum(BOOKING_INTENTS).optional()`, but
`nextAvailableSlotController` (`booking.controller.ts:236-243`) never reads
`parsed.data.intent` and `findNextAvailableSlot` has no `intent` parameter — it
always uses `resolveBookingLeadDays` (new-booking floor). Harmless today because
the only caller (`getNextAvailableSlot` in `CustomerBookingFlowPage`) is the
new-booking flow, but it is a latent trap: a future reschedule caller that
passes `intent=reschedule` would silently get the new-booking lead days. Either
wire it through `findNextAvailableSlot` or drop it from this validator until it
is needed.

### N2. `shiftDateString` duplicates `addDaysToDateString` — `server/src/features/booking/services/staffPicker.service.ts:183`

`shiftDateString` is a byte-for-byte copy of `addDaysToDateString` in
`availability.service.ts:443`. The comment cites service↔service import-cycle
avoidance; a small shared date-util module (both files already import from
sibling services) would remove the copy.

### N3. Two `resolveEffectivePolicy` round-trips per availability request

`availabilityController` runs `resolveBookingLeadDays` / `resolveNoticeLeadDays`
(one policy resolve) in `Promise.all` alongside `getDaySlots`, which does its own
`resolveEffectivePolicy`. Pre-existing pattern (the old `resolveNoticeLeadDays`
did the same), just noting it persists.

### N4. No test for the new Policies field — `client/src/features/booking/pages/PolicyConfigurationPage/PolicyConfigurationPage.tsx:439`

The page has no spec file at all (pre-existing), so the new
"New online booking notice period" input — including the `Number('')` → 0 empty
behaviour and the save round-trip — is untested on the client.

## Test coverage

Added/updated: `availability.service.spec.ts` covers the future-date-not-shifted
bug, today-still-drops-past, reschedule floored by `notice_period_days`, and
new_booking floored by `booking_notice_period_days`; `staffPicker.service.spec.ts`
covers `bookingLeadDays` / `noticeLeadDays` derivation and
`assertMeetsBookingLeadTime` (no-op at 0, 422 same-day at floor 2, accept
far-future); `booking.service.spec.ts` covers Online rejected inside the window,
accepted outside, accepted tomorrow at the default 0, walk-in exempt; validator
specs cover the `intent` enum and `booking_notice_period_days >= 0`. Good
coverage of the intended behaviour.

Gaps for a human to close:

- No test that a past-dated (or earlier-today) Online booking is rejected — it
  currently is not (blocking finding 1).
- No branch-tz midnight-boundary case for `assertMeetsBookingLeadTime`: e.g.
  floor 1, "now" late evening Asia/Manila, slot the next Manila morning but the
  same UTC calendar day — the branch-tz `asDate` comparison should pass it; worth
  pinning.
- Suites were not run here (that is `session-documenter`'s job).
