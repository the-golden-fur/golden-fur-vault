## Verdict: APPROVE WITH NITS

The follow-up commit resolves the one blocking finding and does so without introducing a
regression. `createBooking`'s Online path now rejects a `scheduled_start` earlier than
`Date.now() - PAST_SLOT_GRACE_MS` (15 min) with a 422, placed at the top of the
`if (bookingSource === 'Online')` block — before `resolveEffectivePolicy`, before any
write, and independent of the `booking_notice_period_days` floor (which is a no-op at its

night-span math in the two hotel tests is delta-based so it stays deterministic. Remaining
items are the pre-existing nits already documented by the author.

## Verification of the prior blocking finding

**Blocking #1 (past-dated Online bookings not rejected at default config) — RESOLVED.**

- `booking.service.ts:843-851` adds an unconditional past-slot guard in the Online branch,
  gated only on `bookingSource === 'Online'` and `Date.now() - PAST_SLOT_GRACE_MS`. It does
  not depend on `booking_notice_period_days`, so it fires on a stock deployment (floor 0).
- Placement is sound: it runs before `resolveEffectivePolicy`, before the capacity check,
  and before any INSERT / transaction / free-package consumption, so a rejected past-dated
  request leaves no partial write. `resolveBookingItems` / `resolveFreePackageAward` /
  `resolveDiscountAndPromo` run first but are all read-only resolution — and they already
  ran before the old `assertMeetsNoticeLeadTime` call at this same spot, so the ordering is
  unchanged from pre-branch behaviour.
- Walk-in exemption intact: the guard is inside `if (bookingSource === 'Online')`; the
  walk-in path (`booking_source: 'Walk-in'`, staff-only) never reaches it, and
  `booking.service.spec.ts` still has the "walk-in exempt from the notice window" case.
- New test `booking.service.spec.ts:1873` ("rejects a past-dated Online booking with a 422
  even at the default floor (0)") uses `DEFAULT_POLICY` (`booking_notice_period_days: 0`),
  a `scheduled_start` of `soonIso(-1)`, queues only the pet-ownership row (the guard throws
  before the policy resolve, so no further mock rows are consumed), and asserts both the
  422 and the absence of a `bookings` write. Matches the implementation.
- The stale code comments the prior review flagged (`booking.service.ts:835-837`,
  `staffPicker.service.ts:220-221`) are corrected: the Online block comment now says the
  notice floor "is a no-op at its default of 0" and that the past-slot check plus the floor
  together are the "server-side backstop".

**Regression checks requested by the caller:**

- _15-min grace._ `PAST_SLOT_GRACE_MS = 15 * 60_000`, single use, documented as clock-skew
  / fetch-to-submit slack. A slot up to 15 min in the past is still accepted and then runs
  staff/capacity resolution against a just-started window; this is a deliberate, documented
  tolerance and the Slot Picker never surfaces such a slot. Acceptable, non-blocking.
- _Walk-in exemption._ Confirmed intact (see above).
- _Relative-date fixture flakiness._ `BASE_START_MS = Date.now() + 7 * 864e5` is evaluated
  once at module load. No test in `booking.service.spec.ts` uses `vi.useFakeTimers()` /
  `vi.setSystemTime` (grep: zero hits), so there is no fixture-vs-fake-clock interaction.
  The 7-day margin dwarfs any suite runtime, so the past-slot guard cannot trip on the
  shared fixture. The two hotel tests (`:1531`, `:1570`) derive `scheduled_end` as
  `BASE_START_MS + N * 1440 * 60_000`; `resolveQuantity` is pure delta math
  (`Math.round(totalMinutes / itemDurationMinutes)`), so the 3-night / 1-night assertions
  stay deterministic regardless of the wall-clock time-of-day that `BASE_START_MS` lands
  on. No test asserts on the literal fixture date string.
- _Dropped `intent` on next-slot validator._ `getNextAvailableSlot` in `booking.api.ts:220`
  only ever serialised `branch_id`, `service_category`, `from_date`,
  `slot_duration_minutes`, `pet_weight_class`, `lookahead_days` — never `intent` — so the
  `.strict()` validator will not start 400-ing any existing client call. `BOOKING_INTENTS`
  is still referenced by `availabilityQueryValidator` (`booking.validator.ts:499`), so the
  constant is not left dead.

**Branch-tz midnight-boundary test (prior test-gap note) — ADDED and correct.**
`staffPicker.service.spec.ts:199` pins `assertMeetsBookingLeadTime` with
`booking_notice_period_days: 1`, "now" = 23:30 Asia/Manila (15:30 UTC same day): a slot at
09:00 Manila the next day (different UTC day) is accepted; a slot at 23:45 Manila the same
day is rejected. This exercises the `en-CA` / `Asia/Manila` `asDate` comparison against
`shiftDateString(asDate(now), 1)` exactly as implemented at `staffPicker.service.ts:241-246`.

## Non-blocking findings

### N1. Past-slot guard sits after the pricing/discount resolution it doesn't need — `server/src/features/booking/services/booking.service.ts:843`

The guard only reads `input.scheduled_start` and `Date.now()`, so it could move above
`resolveBookingItems` / `resolveFreePackageAward` / `resolveDiscountAndPromo` to reject a
past-dated request a few reads sooner. No correctness impact (those calls are read-only and
this matches the pre-existing position of the old notice check), purely a micro-optimisation
on the reject path. Leaving it grouped with the rest of the Online logic is also defensible.

### N2. `shiftDateString` still duplicates `addDaysToDateString` — `server/src/features/booking/services/staffPicker.service.ts:184`

Unchanged from the first review; author has documented the import-cycle rationale in the
session `testing.md`. A shared date-util module would remove the byte-for-byte copy.

### N3. Two `resolveEffectivePolicy` round-trips per availability request

Unchanged pre-existing pattern; noted as persisting, documented by the author.

### N4. `PolicyConfigurationPage` still has no spec — `client/src/features/booking/pages/PolicyConfigurationPage/PolicyConfigurationPage.tsx`

The new "New online booking notice period" input (including the `Number('')` → 0 empty
behaviour and the save round-trip) remains untested on the client. Explicitly deferred by
the author as an open item. Non-blocking because the field is a plain number input backed
by a server-validated payload, but a human should track closing it.
