# Pre-PR review — 86-promo-variations-and-spin-wheel

Branch: `feat/promo-variations-spin-wheel`. Run via the `/code-review` skill
(high effort, no inline comments) against the branch's diff versus `dev`.
6 of 7 finder agents completed (Angle A, Angle B, Reuse, Simplification +
Efficiency, Altitude, Conventions); the 7th (Angle C, cross-file tracer)
hit a session rate limit mid-run and didn't report — not re-run given the
other six already covered the branch thoroughly and the two real
correctness findings below were independently surfaced by two different
agents (Angle A and Angle B), which is a strong signal nothing load-bearing
was missed.

## Fixed before opening the PR

1. **Duplicate `promo_ids`/`coupon_ids` could double-apply a single promo**
   (found independently by both Angle A and Angle B). The old design made
   this structurally impossible — `promo_id` was a single scalar. The
   multiselect refactor moved it to `promo_ids: z.array(z.uuid())` without
   carrying over an equivalent uniqueness guard, even though this exact
   validator file already has the identical pattern for `items`
   (`requireNoDuplicateItems`, deduping `serviceIds`/`packageIds`).
   Sending the same promo id twice created two independent candidates fed
   into `applyPromoCap`, so a branch whose stacking cap had room (e.g. a
   `count` cap ≥ 2, or a `percentage`/`flat` cap with enough headroom)
   would apply that one promo twice.
   - Fix: added `requireNoDuplicatePromoOrCouponIds` (mirrors
     `requireNoDuplicateItems`) to both `createBookingValidator` and
     `createBookingGroupValidator` in `booking.validator.ts`, plus a
     `.max(20)` ceiling on both arrays (Angle B's finding #3 — nothing
     bounded how many sequential per-id lookups a single request could
     force in `resolveDiscountAndPromos`).
   - Added test coverage: both validators previously had zero dedicated
     tests for this; added rejection tests for duplicate `promo_ids` and
     `coupon_ids` on each.

2. **`markCouponsRedeemed` had no `is_redeemed = false` guard — a TOCTOU
   double-redemption race** (Angle A). The redemption write trusted the
   ownership/redeemed/expiry check from `getCouponsByIds` moments earlier
   in the same request, with nothing re-checked at write time. Currently
   masked in practice by `booking_promo_selections`'s own
   `booking_promo_selections_coupon_uniq` unique index (a second concurrent
   booking referencing the same coupon fails on THAT insert and rolls
   back), but the redemption function itself had no correctness guarantee
   of its own — a future caller that doesn't go through the same
   insert-then-redeem sequence would have no protection at all.
   - Fix: added `.eq('is_redeemed', false)` to the update, plus an
     affected-row-count check that throws a 409 if any requested coupon
     wasn't actually updated (i.e. it was redeemed by someone else in the
     meantime). Wired that new failure mode into the same
     booking/booking_group rollback path `createBooking`/
     `createBookingGroup` already use for every other post-insert failure
     (delete the just-created booking/group row — `booking_promo_selections`
     cascades on delete, so nothing is left orphaned).
   - Added `customerCoupons.service.spec.ts` — the rewards feature had **no
     test files at all** before this (flagged separately by the
     Conventions agent below); this covers `getCouponsByIds`'s four
     rejection branches and `markCouponsRedeemed`'s new guard.

Re-ran the full server suite after both fixes: 1139/1139 passing (102
files, up from 1125/101 before this review pass), `tsc --noEmit` clean.

## Flagged, not fixed this session (follow-ups)

Judgment call: the two items above are real correctness/money-affecting
bugs and were fixed before opening the PR. Everything below is either a
maintainability/consistency cost or a defense-in-depth improvement on code
that is already correct today — deferred to keep this session's scope to
"ship the feature correctly," not "eliminate every duplication the review
surfaced."

- **Test coverage gap (Conventions agent)**: `server/src/features/rewards/`
  still has no tests for `spinWheel.service.ts`, `spinWheelConfig.service.ts`,
  `rewardsAccess.service.ts`, or `rewards.controller.ts` (only
  `customerCoupons.service.ts` is now covered). No client-side tests exist
  for `SpinWheel`, `AdminSpinWheelConfigPage`, `CustomerRewardsPage`, or
  `PromoCouponMultiSelect` either.
- **Three independent "effective promo cap" implementations, one silently
  wrong (Altitude)**: `catalog.service.ts`'s `getBookingCatalog` merges cap
  rows client-side with a hardcoded `{cap_type:'percentage', cap_value:20}`
  fallback if the default row is missing, while `booking.service.ts`'s
  `getPromoCapRow` and `discountPromoEvaluation.service.ts`'s
  `getEffectivePromoCap` both throw a 500 in that case — a genuine
  preview-vs-reality mismatch if that row is ever deleted. Should
  eventually collapse into one shared fetcher in `promoCap.service.ts`.
- **Coupon redemption still isn't atomic (Altitude)**: unlike `spin_wheel()`
  (a single `SECURITY DEFINER` Postgres function with row locks), "insert
  booking_promo_selections, then redeem the coupon" is two separate
  app-level writes, duplicated near-verbatim between `booking.service.ts`
  and `bookingGroup.service.ts`. This session's fix (guard + rollback)
  closes the double-redemption hole but doesn't make the sequence atomic
  the way the rest of this feature's money-affecting writes are.
- **Reuse duplication**: `DISCOUNT_TYPES` + the "percentage ≤ 100" bound is
  now tripled across `rewards.validator.ts`/`maintenance.validator.ts`/
  `discounts.validator.ts`; `resolveTargetCustomerId` is copy-pasted from
  `creditBalance.service.ts`; `round2` gained an ~12th server copy (in the
  new `promoCap.service.ts`, of all places — the one file meant to
  centralize this) and a 6th client copy (`applyPromoCap.ts`).
- **Efficiency**: `resolveDiscountAndPromos`'s promo loop does sequential
  `await getPromoById` per id instead of batching like the coupon path
  already does; `getBookingForBilling` awaits its two independent queries
  sequentially instead of via `Promise.all`; the two new completion
  triggers re-query the singleton `spin_wheel_config` row per affected
  row instead of once per statement; `CustomerRewardsPage` refetches all
  three of rewards/coupons/spin-credits after every spin instead of
  updating optimistically from the spin result it already has.
- **Simplification**: `promoLabel`/`couponLabel` in
  `PromoCouponMultiSelect.tsx` are copy-paste variants of the same
  percentage-vs-flat formatting; `getPromoCapRow`/`getEffectivePromoCap`
  could collapse into the shared `promoCap.service.ts` alongside
  `applyPromoCap`, which they only ever feed.
- **Minor placement inconsistency**: `client/src/shared/utils/promoEligibility.ts`
  has exactly one consumer (`CustomerBookingFlowPage.tsx`), same as the
  sibling `client/src/features/booking/utils/applyPromoCap.ts` — the two
  were placed inconsistently (`shared/` vs. `features/booking/utils/`)
  despite identical justification in their own header comments.

## Verdict

The two things that matter for correctness on a money-affecting feature —
promo/coupon eligibility and the stacking cap — were reviewed as "handled
well" by the Altitude pass: `isPromoCurrentlyEligible`, `applyPromoCap`,
and the unified `EvaluatedPromo{promoId|couponId}` shape genuinely
replaced what would otherwise have been scattered special-cases. The two
real bugs found (duplicate-id double-application, coupon TOCTOU) are
fixed and tested. Everything else is consistency/efficiency debt typical
of a first pass at a large feature, tracked above rather than silently
dropped.
