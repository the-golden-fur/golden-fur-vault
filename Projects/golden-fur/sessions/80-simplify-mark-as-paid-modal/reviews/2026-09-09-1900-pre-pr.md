## Verdict: APPROVE — no Blocking findings; 2 of 4 non-blocking findings actioned

items were raised; two were fixed, two are deliberate no-ops (recorded below).

## Findings

### F1 — narrowing `recordTransactionPaymentValidator` to `COUNTER_PAYMENT_METHODS` was scope creep and removed a real path — FIXED (reverted)

The earlier medium pass suggested restricting the "Mark as paid" endpoint to
the 5 counter methods (the pre-existing `z.enum(PAYMENT_METHODS)` accepted
GCash/Maya and the old code settled them immediately). The high pass flagged
that as a **behaviour regression** unrelated to this task — a cashier
confirming a counter GCash/Maya QR payment against an existing Pending
`booking_payment` row would start getting HTTP 400 with nothing in the diff
re-establishing that path.
**Fix:** reverted. `recordTransactionPaymentValidator` is back to
`z.enum(PAYMENT_METHODS)`, `PAY_MODAL_METHODS` back to
`[...PAYMENT_METHODS, 'Credit']`, the client-side `COUNTER_PAYMENT_METHODS`
mirror removed. The validator docblock is corrected to describe what the code
actually does instead of the aspirational "GCash/Maya excluded" wording that
was there before. Method breadth is now byte-for-byte unchanged from `dev` —
this PR only touches the field count.

### F2 — `payTransactionWithCredit` validated `amountApplied` after two DB round-trips; bounds logic duplicated — FIXED

`recordTransactionPayment` bounds-checked before its `loadBookingPaymentStatus`
call; `payTransactionWithCredit` did the same check only after
`loadBookingPaymentStatus` + `pendingBalanceTxnIds`, and the
`round2` / `<= 0` / `> total + 0.001` block was copy-pasted between the two.
**Fix:** extracted `resolveAmountApplied(amountApplied, total)` in
`transactionPayment.service.ts`; both functions call it immediately after the
Pending check, before any DB work.

### F3 — client "amount paid" validation lives in two modals and the customer one skips it for GCash/Maya — NOT ACTIONED

`CustomerTransactionHistoryPage.confirmPay` validates only inside
`if (payMode === 'credit')`, relying on `selectPayMode()` snapping the field
back to full + the `disabled` attribute for GCash/Maya (which don't send
`payAmount` at all — `payForBooking` takes `pay_in_full`). The cashier modal
validates unconditionally. A shared client validator is marginal here (two
different components, different submit paths) and an invalid `payAmount` on
the GCash/Maya branch is inert. Left as-is; noted for a future "partial
online payment" change, which would need the guard.

### F4 — `p_cash_tendered: null` still passed to `settle_transaction` — NOT ACTIONED (intended)

The RPC keeps the 7-arg signature and ignores the param (the transaction has
no tendered/change column). Passing `null` with the existing explanatory
comment is correct without a migration; dropping the arg would need a
signature-changing migration that is out of scope. Left with the comment.
