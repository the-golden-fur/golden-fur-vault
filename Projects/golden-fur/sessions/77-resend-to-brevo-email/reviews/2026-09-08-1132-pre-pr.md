## Finding 1 — spurious combined "bookings confirmed" email on payment reversal (fixed)

`recomputeBookingGroupPaymentStatus` (`booking.service.ts`) was adding members
to the combined-email list from a re-derived `status === 'Pending' &&
booking_source === 'Online'` check. On a payment reversal (all group payments
voided → members bulk-set back to `payment_status: 'Pending'`),
`applyFirstBookingPaymentSideEffects` early-returns and sends nothing, but a
member still sitting in the normal confirmed state (`status 'Pending'`, Online)
would be pushed into `newlyConfirmed` and re-emailed a stale confirmation.

**Fix:** the push condition now also requires `updated.payment_status !==
'Pending'`, mirroring `applyFirstBookingPaymentSideEffects`'s own send guard
exactly. No dedicated regression test — `recomputeBookingGroupPaymentStatus`
has no unit-test scaffold today (it's mocked wholesale by every consumer), and
the guard is a one-line mirror of the already-tested
`applyFirstBookingPaymentSideEffects` condition; the combined-vs-per-booking
happy path is covered by `bookingGroup.service.spec.ts` cases (f)/(g).
Flagged in `testing/testing.md` → Open items.

## Finding 2 — scheduler cadence didn't match its own docstring / migration comment (fixed)

`careLogDailyReport.job.ts` was implemented as a single daily 21:00
`setTimeout` (copied from `promoExpiry.job.ts`), but the docstring and
migration `20260908182`'s comment described an hourly poll whose
`care_log_daily_reports` claim ledger guards "overlapping poll runs / a server
restart" — resilience the once-a-day timer did not provide (a restart at 21:40
lost that evening's summaries until the next night).

**Fix:** the scheduler is now a genuine hourly poll; `shouldRunAt(now)` gates
the batch to `getHours() >= 21`. Every tick after the first is a cheap no-op
for stays already claimed today, so the ledger now earns its rationale. Job
docstring, `app.ts` comment, and the migration comment updated to match.
`shouldRunAt` replaces the removed `msUntilNextRun`; spec updated.

## Finding 3 — stale "via Resend" comments in client code (fixed)
