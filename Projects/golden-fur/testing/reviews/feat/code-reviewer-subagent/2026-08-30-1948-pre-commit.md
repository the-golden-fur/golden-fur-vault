## Non-blocking findings

### N1. `AGENTS.md` documents a hook that lives in a gitignored file — `AGENTS.md:98-104`

The new paragraph states that a `PreToolUse` hook in
`.claude/settings.local.json` "is a backstop" that blocks `git commit` /
`git push` / `gh pr create`. `.claude/settings.local.json` is
`.gitignore`d (confirmed via `git check-ignore`) and is not part of this
commit, so for every other contributor, machine, or AI tool that reads the
committed `AGENTS.md` the described backstop does not exist. The hook is
currently present only in the author's local settings. If it is meant to be
a repo-wide safety net it belongs in the tracked `.claude/settings.json`;
if it is deliberately personal, `AGENTS.md` should not present it as
existing infrastructure (say "optionally, add a local hook…" or drop the
paragraph). The same claim is repeated in the commit message body.

### N2. Two-dot vs three-dot diff range in the skill prose — `.agent/skills/pr-to-dev.md:9`, `.agent/skills/commit.md:38`

`pr-to-dev.md` tells the caller to review "the full `dev..HEAD` diff" and
`commit.md`'s publish section says "the full `<base>..HEAD` diff", while
the canonical `code-reviewer.md` (correctly) uses `git diff <base>...HEAD`
(three-dot). For `git diff` the two forms differ when the base has moved
on; a reader following the skill literally could diff the wrong range. Make
the skill wording match the agent file (`dev...HEAD`).

### N3. Branch type vs work type — branch `feat/code-reviewer-subagent`

Per `.agent/skills/branch-naming.md` the types table, tooling/config work
is `chore/`. The commit itself is correctly `chore(agents): …`, so the
branch prefix is inconsistent with both the table and the commit. Cosmetic;
no action needed if the branch is short-lived.

### N4. Latent same-class flake in the untouched first test — `client/src/features/veterinary/components/ScheduleFollowUpModal/ScheduleFollowUpModal.spec.ts:158-179`

The working-tree fix correctly guards the two tests that failed in CI. The
first test ("locks pet/owner/branch/category…") still reads
`screen.getByRole('option', { name: /Wellness Exam/ })` synchronously,
relying on the `listBranches` promise (awaited via `findByText('Makati')`)
having flushed the *separate* `getBookingCatalog` promise's state update by
then. That happens to hold today but is the same ordering assumption the
fix removes elsewhere. Consider applying the same
`await screen.findByRole('option', …)` there while you are in the file.

## Test coverage

- Working tree: `ScheduleFollowUpModal.spec.ts` adds
  `await screen.findByRole('option', { name: /Wellness Exam/ })` before
  `user.selectOptions(serviceSelect, 'service-1')` in two tests (the
  create-and-link test and the booking-failure test), with an explanatory
  comment. Verified against `ScheduleFollowUpModal.tsx`: the `<select>`
  mounts immediately with only the "Select a service…" placeholder;
  `services` is filled after the awaited `getBookingCatalog` resolves and a
  re-render, so `findByRole('combobox')` can resolve before `service-1`

  the rendered label `Wellness Exam (₱500.00)`, and there is exactly one
  such option, so `findBy` (single-match) is appropriate. Fix is correct
  and minimal.
- No behavioural code changed, so no new product tests are expected.
- Suites were **not run** here (that is `testing-documenter`'s job) — this
  was a read of the test and the component only.
