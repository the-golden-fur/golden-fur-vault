## Verdict: APPROVE (findings addressed)

The change adds a server-hydrated `customer_name` to the transaction-history
list, a new shared `FilterSortBar` (Notion-style filter/sort tiles) +
`ViewSwitcher` + status-grouped `TransactionBoard`, and rewires both the
cashier `TransactionHistoryTable` and the customer `CustomerTransactionHistoryPage`
onto them. The server change is sound (no findings). The review surfaced four
client-side findings; all four were fixed before this report.

## Findings

### F1 — Date filter tile silently scoped the list to the current month — FIXED

`DATE_FIELD.defaultValue` was `{ preset: 'this_month' }`. Clicking
**Filter → Date** to look up an older transaction created the tile with that
default; `deriveServerParams` immediately resolved it to `date_from`/`date_to`
for the current month and the effect refetched, hiding every out-of-month row
until the user knew to open the tile and switch to "All dates". A regression
from the previous always-all-time date inputs, on both the staff and customer
pages.
**Fix:** `transactionFilterFields.ts` — `DATE_FIELD.defaultValue` is now
`{ preset: 'all', from: null, to: null }`. Adding the tile restricts nothing;
the user picks a preset/range in the popover. `formatDateRange` already
renders `'all'` as "All dates".

### F2 — history fetch effect never cleared `error` and had no rejection handler — FIXED

The `.then` only ever called `setError(<truthy string>)` / `setIsLoading(false)`
— never `setError(null)` on a subsequent success, and there was no `.catch`.
After one transient failure (500, expired token, offline) the stale error
banner stuck forever even once a later request succeeded; a thrown fetch
(network error) left the page on "Loading transactions..." with an unhandled
rejection. Same shape in `CustomerTransactionHistoryPage.tsx`.
**Fix:** both effects now `setError(null)` on success and add a `.catch` that
clears the loading state and shows a "please try again" message. (Pre-existing
latent bug in the old code; fixed now since the effect was being rewritten
anyway.)

### F3 — `filterFields` / `serverFilterKey` recomputed every render — FIXED

`buildStaffFilterFields({...})` allocated a fresh array + option arrays on
every render (every search keystroke) and was passed straight into
`FilterSortBar`; `serverFilterKey = JSON.stringify(deriveServerParams(...))`
also ran every render, calling `resolveDateRangePreset(new Date())` for any
date tile — which across a UTC-midnight boundary could change the key string
between two renders and trigger a spurious refetch.
**Fix:** `TransactionHistoryTable.tsx` / `CustomerTransactionHistoryPage.tsx`
— `serverFilterKey` is `useMemo`'d on `[filterTiles]`; `filterFields` is
`useMemo`'d on `[customers, pets, hasCustomerFilter]`.

### F4 — customer-portal board cards for misc sales were focusable no-ops — FIXED

`CustomerTransactionHistoryPage` passes `onCardActivate`, so `TransactionCard`
set `role="button"` / `tabIndex={0}` / pointer cursor on **every** card — but
`onCardActivate` guards `if (transaction.booking_id)`, so a
`miscellaneous_sale` card (no booking) announced as a button and did nothing
on click/Enter.
**Fix:** `TransactionBoard.tsx` — a card is only made activatable when
`onCardActivate && transaction.booking_id`.

## Not findings (noted)

- **Server `customer_name` hydration** — `select('*')` includes `customer_id`;
  the dedup + `Map` + `?? null` fallback is correct and matches the repo's
  no-FK-embed convention (`bookingDetails.service.ts`, `messaging.service.ts`).
  Service-role client → archived customers resolve.
- **3-column board** — `payment_status` enum is exactly
  `{Pending, Partially Paid, Fully Paid}`, so no row is dropped.
- **Amount formatting** — board uses `formatCurrency` (`₱`), tables keep
  `PHP {n.toFixed(2)}`. Deliberate (existing table strings + spec assertions);
  documented in `testing.md`.
