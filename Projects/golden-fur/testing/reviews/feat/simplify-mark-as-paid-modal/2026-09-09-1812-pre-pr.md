# Code review — `feat/simplify-mark-as-paid-modal`

- **Trigger:** pre-pr / pre-commit
- **Base:** `dev` (merge-base `b6c5b81`)
- **Reviewed:** uncommitted working tree — 12 modified files under
  `client/src` / `server/src` (no migrations)
- **Reviewer:** `/code-review` (medium) — read-only, did not author the change
- **Change under review:** collapse the cashier "Mark as paid" modal to a
  single **Amount paid (PHP)** field (drop the separate "Cash tendered" input
  + "Change" line, which the transaction never stored); add the same single
  editable field to the customer Pay modal, editable for the **Account
  credit** method only (GCash/Maya stay full-amount). Thread `amount_applied`
  into the pay-with-credit path.

## Verdict: APPROVE (findings addressed)

Server: `recordTransactionPaymentValidator` loses `cash_tendered` and its
Cash refinement; `recordTransactionPayment` drops the
`resolvePaymentConfirmation` call and `changeAmount` from its result and
passes `p_cash_tendered: null` (RPC signature unchanged, param already
ignored by the RPC body). `payTransactionWithCredit` gains an optional
`amountApplied` cap (`min(available, requested)`, `requested` bounded by the
charge). Client: `PaymentMethodForm` gains `hideCashTendered`; both modals
render one money field. No migration.

Two findings were raised and both fixed before this report; two further
items are pre-existing and explicitly out of scope.

## Findings

### F1 — validator docblock claimed GCash/Maya were excluded but `z.enum(PAYMENT_METHODS)` still accepted them — FIXED

`recordTransactionPaymentValidator` accepted every `PAYMENT_METHODS` value
(GCash/Maya included) while its docblock — old and new — said those were
"deliberately excluded". Removing the `resolvePaymentConfirmation` call took
away the last method-aware step, so a cashier could pick GCash in the "Mark
as paid" modal and `settle_transaction` would unconditionally flip the row to
Fully Paid with `payment_method='GCash'` and no PayMongo confirmation —
exactly the "slot held without a real payment" case the advisor flagged.
**Fix:** the validator now uses `z.enum(COUNTER_PAYMENT_METHODS)` (the
existing 5-method constant that already documents this restriction);
`COUNTER_PAYMENT_METHODS` was mirrored into the client `billing.types.ts` and
`PAY_MODAL_METHODS` is now `[...COUNTER_PAYMENT_METHODS, 'Credit']`, so the
dropdown no longer offers GCash/Maya here.

### F2 — "A PHP X balance payment will be created" preview was wrong for the credit path — FIXED

The preview computed `total − enteredAmount`, but `payTransactionWithCredit`
caps the applied amount at `min(availableCredit, requested)`, so the real
leftover is `total − min(available, entered)`. With PHP 100 credit, entering
200 against a 500 charge previewed a "PHP 300" balance while the server would
spawn a PHP 400 one.
**Fix:** for the credit method both modals now show a number-free message
("Whatever the available credit does not cover will be left as a balance
payment"). The exact-figure preview is kept only for the counter-cash path,
where `settle_transaction` applies `amount_applied` verbatim.

## Not findings — pre-existing, out of scope

- **Full-amount credit pay with insufficient credit spawns a balance row
  with no post-payment toast.** True before this change too
  (`pay_transaction_with_credit` has clamped to available credit and spawned
  a leftover since `20260902164`); the response's `leftover` is not surfaced
  by either the old or new UI. Not a regression from this change.
- **Board view + an active Status filter tile shows empty columns.** In
  `TransactionBoard` / the status-filter wiring from session 78; untouched
  here.
