## Verdict: CHANGES REQUESTED

The change drops `bookings.payment_stage` and replaces it with a
`payment_status` rollup of settled `booking_payment` transactions, adds three
SECURITY DEFINER RPCs (`settle_transaction`, `add_booking_payment`,
`redeem_credit`), three new `/billing` endpoints plus a `TransactionsPage`,
de-stubs credit redemption, folds the deleted Payments Queue's Misc
start/complete + pet-assessment modal into the receptionist queue, and adds a
configurable cancellation-to-credit conversion rate. The migrations and the
RPC-side rollup math are sound and the destructive column drop is handled
carefully. The blocking problems are all in how the *three* payment entry
points now interact: `createInitialBookingCharge` fires on every booking, but
only the cashier `recordTransactionPayment` path was taught to settle that
charge — the customer portal path and the cashier checkout path were not, so
they now either double-charge or hard-fail. There is also a non-atomic
credit-then-settle sequence that can silently burn a customer's credit.

## Blocking findings

### 1. Cashier checkout (`POST /billing/checkout`) is now unreachable for every non-Veterinary booking — `server/src/features/billing/services/checkoutAggregation.service.ts:180`

`createBooking` now calls `createInitialBookingCharge` for every booking with
`service_category !== 'Veterinary'` and `initialChargeAmount > 0`
(`booking.service.ts:1057`), inserting a `Pending` `booking_payment`
transaction at creation time. `checkoutBooking` still opens with a guard that
rejects if *any* transaction row exists for the booking:

```
if (existingTransactions && existingTransactions.length > 0) {
  throwWithStatus(409, `This booking already has a payment record (...)`);
}
```

So `checkoutBooking` will now 409 for essentially every real booking. The
`CashierCheckoutPage` (route `/staff/billing/checkout/:bookingId`), its
"Checkout & Billing" dashboard tile, `previewCheckout`, and
`checkoutAggregation.service.ts` are all still wired and unchanged — this is a
live, advertised cashier flow that is now dead on arrival. Either the checkout
flow is intentionally superseded by `TransactionsPage` and its page / route /
tile / service / validator / controller should be removed, or the guard needs
to distinguish "an unsettled initial charge exists" (settle it / supersede it)
from "a real payment record exists". Right now the repo is in neither state.

### 2. Customer portal payment creates a second charge instead of settling the initial one — `server/src/features/billing/services/customerBookingPayment.service.ts:110`

`payForBooking` (the customer "Pay" button on `CustomerBookingsPage`) inserts a
*new* `Pending` `booking_payment` transaction rather than settling the
`Pending` charge `createInitialBookingCharge` already wrote. Result for the
normal happy path (customer books, then pays online):

- Booking ends up with two `Pending` `booking_payment` rows.
- The webhook confirms the portal row; `recomputeBookingPaymentStatus` rolls
  up `payment_status` from it.
- The original `createInitialBookingCharge` row is never referenced again — it
  sits `Pending` forever, shows on `TransactionsPage` as "Due payment", and a
  cashier who settles it double-charges the customer (and inflates
  `confirmedAmountPaid` on a later cancellation, minting excess credit).

The cashier path (`recordTransactionPayment`) and the webhook path
(`recomputeBookingPaymentStatus`) were both reworked to operate on the
existing charge; the customer path was not. It should settle / replace the
initial charge, not add to it.

### 3. `payForBooking` amount math ignores discount and promo — `server/src/features/billing/services/customerBookingPayment.service.ts:63,66`

Every branch computes the charge from `booking.total_price`, never
`total_price - discount_amount - promo_amount` (the `netTotal` the rest of the
rework, including `settle_transaction` / `add_booking_payment` /
`recomputeBookingPaymentStatus`, consistently uses). A booking created with a
staff discount or a promo is charged the *gross* amount online. The mirrored
"Amount due" display in `CustomerBookingsPage.tsx:462` has the same bug, so
the customer is shown and charged the wrong (higher) number. The pre-existing
code had this latent, but the `payment_stage === 'Paid in Advance'` →
`payment_status === 'Partially Paid'` broadening (line 60) now also routes any
arbitrary partial payment through the `total_price - (downpayment_amount ?? 0)`
branch: for a non-downpayment booking `downpayment_amount` is `null`, so a
customer who already made a partial payment is billed the full `total_price`
again.

### 4. `payTransactionWithCredit` redeems credit and settles in two separate RPC calls — no rollback — `server/src/features/billing/services/transactionPayment.service.ts:242-267`

`redeem_credit` (decrements `credit_balances`, writes a signed redemption row)
and `settle_transaction` are two independent `supabase.rpc(...)` calls. If
`settle_transaction` fails — e.g. the transaction was settled by a concurrent
cashier between the `payment_status !== 'Pending'` check at line 211 and this
call, which raises `settle_transaction: transaction ... is already Fully Paid`
— the credit has already been redeemed and there is no compensating re-credit.
The customer silently loses the redeemed amount. This is a money path with no
test for the failure branch. Wrap both in one SECURITY DEFINER RPC, or add an
explicit re-credit on `settleError`.

### 5. A fully-discounted / fully-promo'd Online booking is stuck unpayable and cannot be started — `server/src/features/booking/services/booking.service.ts:1057`

`createInitialBookingCharge` is guarded by `initialChargeAmount > 0`. A promo
with a 100% `Percentage` value (nothing in `resolveDiscountAndPromo` clamps
this) drives `netTotal` to 0, so no charge is created and `payment_status`
stays `Pending`. Then:

- `startBooking` (line 1487) refuses an Online non-Veterinary booking while
  `payment_status === 'Pending'` → the booking can never be checked in.
- `addBookingPayment` → `add_booking_payment` raises (`amount ... exceeds
  remaining balance 0`).
- `payForBooking` → 409 "nothing left to pay".

The only escape is an Admin `overrideBookingStatus`. The zero-owed case should
be treated as "nothing to collect" (e.g. create the booking `Fully Paid`, or
let `startBooking` pass when `netTotal <= 0`).

## Non-blocking findings

### N1. `add_booking_payment` "remaining" ignores outstanding Pending charges — `supabase/migrations/20260901154_...sql:53`

`v_remaining := v_net - v_settled` where `v_settled` only counts non-Pending
rows. With the always-present initial `Pending` charge (and any prior unsettled
balance charge), a staff member can `add_booking_payment` up to the full net
total *again*, stacking `Pending` charges whose sum exceeds the booking total.
`settle_transaction` then happily settles each one (it only blocks
already-`Fully Paid` rows), capping `payment_status` at `Fully Paid` while the
customer is over-collected. Consider subtracting outstanding `Pending`
`booking_payment` amounts from `v_remaining`, or blocking a new charge while
one is unsettled (the client already hides "Add a payment" when `anyPending`,
but the RPC/endpoint is not guarded).

### N2. `settle_transaction` `p_cash_tendered` is accepted and silently dropped — `supabase/migrations/20260901153_...sql:25`

Documented in the header comment, but it means change-due is computed only in
`resolvePaymentConfirmation` (app side) and never persisted — no audit trail of
tendered/change for a cash counter payment. Pre-existing gap, but the rework is
the moment this becomes the primary cash path.

### N3. `TransactionsPage` loads the entire transaction history unfiltered — `client/src/features/billing/pages/TransactionsPage/TransactionsPage.tsx:78`

`getTransactionHistory({})` with no filter and no pagination. It replaces a
focused queue; over time this page renders every settled transaction ever, and
there is no "pending only" filter. `PaymentMethodForm` also offers GCash/Maya,
which `recordTransactionPaymentValidator` (`COUNTER_PAYMENT_METHODS`) rejects
with a 400 — the form should not present them here.

### N4. Statutory discount at booking is no longer tied to an in-person payment — `server/src/features/booking/services/booking.service.ts:508`

The "Cash only" restriction on `resolveDiscountAndPromo` was removed. A
Senior/PWD discount can now be applied by a money-handling role at booking time
and then the booking paid entirely online, with no cashier ever seeing the ID
at payment. The `discountIdVerified` attestation + role gate remain, so this is
likely acceptable, but per `discount-senior-pwd-compliance` it is worth a
conscious sign-off that the attestation alone satisfies the
ID-verification-logging expectation.

### N5. `payForBooking` `Partially Paid` comment vs behaviour — `client/src/features/booking/pages/CustomerBookingsPage/CustomerBookingsPage.tsx:176`

The retained comment still says "payForBooking always charges the remainder
regardless" — it does not (finding 3). Update the comment or the code.

### N6. Positional supabase mocks in `transactionPayment.service.spec.ts` — `server/.../transactionPayment.service.spec.ts:37`

`queueFrom` depends on the exact `supabase.from()` call sequence and a builder
that only implements `select`/`eq`/`update`/`maybeSingle`/`then`. It works
today but will break confusingly if a service function adds a `.neq()` /
`.insert()` / reorders a read. Low priority, but the credit failure path
(finding 4) and `recomputeBookingPaymentStatus` have no coverage at all.
